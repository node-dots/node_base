# Автоматична документація API: Zod → OpenAPI → Swagger

Оновлено 12 жовтня 2026 року. Приклад для команди — реалізований модуль groups.

## Що тепер автоматично

Swagger UI отримує OpenAPI-документ, згенерований із JavaScript і Zod під час створення застосунку. Сервер не читає `docs/api/openapi.json`. Типи, обов’язкові поля, межі чисел і рядків, enum та заборона невідомих полів беруться зі схем. Версія API береться з `package.json`.

Розробник описує явно метод, адресу, призначення операції, схеми запиту/відповіді, HTTP-статуси та заголовки. Express routes, controller і бізнес-політики не скануються автоматично. Новий маршрут не з’явиться у Swagger без його реєстрації. Перетворення Zod також не описує довільні бізнес-перевірки чи всі можливі refinement/transform; такі правила пояснюємо в описі операції й перевіряємо тестами.

## Де що лежить

| Файл | Призначення |
|---|---|
| `src/openapi/zod.js` | Один раз підключає розширення `@asteasolutions/zod-to-openapi` до Zod до створення схем |
| `src/modules/groups/group.schema.js` | Вхідні схеми й схеми публічних відповідей; вхід використовується також validateBody |
| `src/modules/groups/group.openapi.js` | Опис чотирьох операцій groups із посиланнями на ці схеми |
| `src/openapi/common.js` | Технічні операції, загальні схеми помилок, заголовки й helper JSON-відповіді |
| `src/openapi/document.js` | Створює новий registry, реєструє описи модулів і генерує OpenAPI 3.1 |
| `src/middleware/apiDocumentation.js` | Віддає згенерований документ і ресурси Swagger UI |
| `scripts/export-openapi.js` | За потреби записує актуальний експорт у `docs/api/openapi.json` |

```text
module.schema.js + module.openapi.js
                  ↓
       openapi/document.js
                  ↓
      GET /api/v1/openapi.json
                  ↓
             /api-docs/
```

Документ генерується один раз для кожного створеного Express-застосунку, не на кожний HTTP-запит. Схеми не відкривають MongoDB та не запускають бізнес-команди. Не додаємо виклики генератора в controller, service або repository.

## Як змінити поле наявної операції

1. Змінити схему в `group.schema.js`. Межі беруться з constants, а не дублюються в OpenAPI.
2. Для поля додати `.meta({ description: 'Пояснення українською', example: ... })`, коли пояснення допомагає користувачу API. Для іменованої схеми — `.meta({ id: 'CreateGroupInput' })` або іншою унікальною англійською назвою.
3. Якщо змінюється відповідь, оновити також DTO та її Zod-схему. Генератор не виводить схему з функції DTO.
4. Виконати `npm run check` і відповідну MongoDB-перевірку; відкрити Swagger після перезапуску.

У `dev` сервер перезапускається через watch. У `start` чи `debug` перезапустіть процес після зміни коду. Далі оновіть сторінку Swagger. Команда експорту для роботи Swagger не потрібна.

## Як додати нову операцію

Схеми, що реєструються в OpenAPI, імпортують розширений Zod з `src/openapi/zod.js`. Для файла в папці модуля:

```javascript
import { z } from '../../openapi/zod.js';
```

У `<module>.openapi.js` додаємо `registry.registerPath`. Реальний зразок створення групи:

```javascript
registry.registerPath({
  method: 'post',
  path: '/api/v1/groups',
  operationId: 'createGroup',
  tags: ['Групи'],
  summary: 'Створити чернетку групи',
  request: {
    body: {
      required: true,
      content: { 'application/json': { schema: createGroupSchema } },
    },
  },
  responses: {
    201: jsonResponse(groupResponseSchema, 'Групу збережено в MongoDB.'),
    400: { $ref: '#/components/responses/BadRequest' },
  },
});
```

Це скорочений приклад. Повний опис у `group.openapi.js` також містить Location і помилки 413, 422, 429, 500. Для нового сценарію перелічіть його реальні відповіді. `operationId` та ID схеми мають бути унікальними в усьому API.

Шлях Express `/groups/:id` у повному OpenAPI-шляху записується як `/api/v1/groups/{id}`; параметр описуємо Zod-об’єктом у `request.params`. Query-параметри — у `request.query`. Ця документація сама не підключає валідацію до Express: відповідний middleware чи перевірка service/repository мають бути реалізовані явно.

Для нового модуля експортуємо `register<Module>Documentation(registry)` та викликаємо її в `src/openapi/document.js`. Реальний router окремо реєструємо в `src/modules/index.js`. Обидві реєстрації потрібні: документація і виконання запитів мають різні відповідальності.

Нові права JWT не додаються автоматично. Після реалізації login потрібно зареєструвати security scheme і явно описати захищені операції разом із реальною перевіркою доступу. Зараз авторизації немає, тому Swagger її не обіцяє.

## Схеми відповіді та тести

Схема відповіді описує саме дозволені поля DTO. Не експортуємо Mongoose-модель як публічну схему: це може додати внутрішні чи секретні поля. Група використовує ті самі базові поля, що вхід, і додає `id`/`status`; інший модуль може мати зовсім різні request/response.

У production відповідь не проходить додатковий Zod parse на кожному запиті. Відповідність перевіряємо API/integration-тестами. Поточний `documentation.test.js` перевіряє схеми реальних відповідей списку, створення, summary та помилки; обмеження входу, дев’ять операцій, унікальність operationId, відсутність нерозв’язаних `$ref` і повторюваність генерації. Тести не гарантують автоматично правильність кожного майбутнього маршруту — додайте відповідні сценарії при його реалізації.

## Експорт і команди Windows/macOS

Для браузера достатньо звичайного запуску за [окремою інструкцією](06_Local_Startup.md). Адреси не змінилися: `/api-docs/` та `/api/v1/openapi.json` на поточному порту сервера.

Для передачі контракту іншому інструменту виконайте з кореня проєкту:

```bash
npm run docs:export
```

У PowerShell:

```powershell
npm.cmd run docs:export
```

Експорт не потребує запущених API, Docker чи MongoDB. `docs/api/openapi.json` — згенерована копія; не редагуйте її вручну. Якщо передаєте або комітите експорт після зміни API, оновіть його цією командою. Swagger завжди використовує контракт із коду, навіть якщо експорт не оновлений.

Нову залежність зафіксовано в package-lock.json; іншим учасникам після отримання змін слід виконати `npm ci` / `npm.cmd ci`. Окремий Swagger-сервер не потрібний, зовнішній validator вимкнений.
