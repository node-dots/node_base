# Узгоджені вимоги до інформаційної системи приватного дитячого садка

Версія 2.1 · 12 жовтня 2026 року · Навчальний проєкт команди з 8 студентів.

Цей документ визначає, яку систему будує команда, які правила вона виконує та як перевірити результат. Він об’єднує початкові завдання, фінансовий приклад, архітектурні рішення, правила доступу та результати їх повторного перегляду. Суперечливі питання нижче мають одне рішення для першої завершеної версії.

Мета — робочий і зрозумілий backend із правильними бізнес-правилами. Команда повинна вміти пояснити власний код, запустити систему та продемонструвати основні сценарії. Повноцінна бухгалтерія, кадрова система та математичний оптимізатор не є метою проєкту.

**Завдання:** [TASK-001](../planning/tasks/10_Jira_Backlog.md#task-001).

Спільні правила якості й доступу обов’язкові для всіх задач, навіть якщо біля розділу названі лише основні.

При зміні правила оновлюємо його тут і пов’язані картки; при розбитті задачі зберігаємо посилання на нові картки.

## 2. Мета, користувачі та результат

**Завдання:** [TASK-040](../planning/tasks/10_Jira_Backlog.md#task-040).

Розробити backend — серверну частину інформаційної системи приватного дитячого садка. Доступ до операцій надає REST API — HTTP-інтерфейс для роботи з ресурсами й командами.

Система охоплює людей, облікові записи, дітей і представників, групи, кімнати, персонал, дисципліни, розклад, харчові дані, тарифи, пільги, рахунки, платежі, витрати, звіти та фінансові сценарії.

Кінцевий результат містить:

1. Backend із зберіганням у MongoDB та відтворюваним локальним запуском.
2. Автентифікацію, ролі та доступ до дозволених записів і полів.
3. Операції зарахування, переведення, нарахування, підтвердження платежів і публікації розкладу.
4. Автоматичні звіти на MongoDB Aggregation Framework — механізмі групування й обчислення даних у базі.
5. Генератор чернетки розкладу та обмежене порівняння фінансових сценаріїв.
6. OpenAPI — опис адрес, схем, авторизації та відповідей API — зі Swagger UI для перегляду.
7. Тести основних правил, доступу та конкурентних операцій.
8. Окрему допоміжну панель лише для перегляду результатів.

Продуктовий frontend, кабінет батьків і мобільний застосунок не розробляємо. Сценарії показуємо через Swagger UI, HTTP-запити та допоміжну панель.

## 4. Люди, облікові записи та персонал

**Завдання:** [TASK-006](../planning/tasks/10_Jira_Backlog.md#task-006), [TASK-012](../planning/tasks/10_Jira_Backlog.md#task-012), [TASK-013](../planning/tasks/10_Jira_Backlog.md#task-013), [TASK-014](../planning/tasks/10_Jira_Backlog.md#task-014).

<a id="req-4-1"></a>

### 4.1. Людина

**Завдання:** [TASK-006](../planning/tasks/10_Jira_Backlog.md#task-006).

Одна людина має один запис `people`: прізвище, ім’я, за потреби по батькові, контакти та статус. Може одночасно бути представником дитини й працівником. Один представник може бути пов’язаний із кількома дітьми.

Профіль працівника `employee` та обліковий запис `account` необов’язкові. Працівник без облікового запису бере участь у роботі садка, але не входить до API. Створення дубля людини для кожної ролі заборонене.

<a id="req-4-2"></a>

### 4.2. Обліковий запис

**Завдання:** [TASK-006](../planning/tasks/10_Jira_Backlog.md#task-006), [TASK-012](../planning/tasks/10_Jira_Backlog.md#task-012), [TASK-013](../planning/tasks/10_Jira_Backlog.md#task-013).

Обліковий запис містить нормалізований унікальний email для входу, хеш пароля, перелік ролей, ознаку дозволеного входу та версію токенів. Публічної реєстрації немає; записи створює адміністратор.

Статус профілю, стан працівника та блокування входу — окремі поняття. Блокування входу не видаляє людину, не звільняє працівника та не прибирає його з групи автоматично.

<a id="req-4-3"></a>

### 4.3. Працівник

**Завдання:** [TASK-014](../planning/tasks/10_Jira_Backlog.md#task-014), [TASK-024](../planning/tasks/10_Jira_Backlog.md#task-024), [TASK-029](../planning/tasks/10_Jira_Backlog.md#task-029).

Профіль містить посаду, стан зайнятості, дати початку/завершення роботи, зарплатні параметри, доступність та одну дисципліну для викладача. Для інших посад дисципліна не задається.

Основні посади: вихователь, помічник, викладач, менеджер, адміністратор. Для фінансового прикладу також потрібні психолог, охоронець і прибиральник. Посади є довідником; роль доступу не визначає зарплату.

Стани працівника включають роботу, відпустку, лікарняний і звільнення. Відпустка та лікарняний обмежують доступність у розкладі. Відпускні й денні зарплатні перерахунки не обчислюємо.

Звільнення призначеного вихователя або помічника допускається після заміни чи зняття призначення з неактивної групи. Зміна викладача, дисципліни або доступності перевіряється проти майбутнього опублікованого розкладу.

## 5. Ролі та доступ

**Завдання:** [TASK-012](../planning/tasks/10_Jira_Backlog.md#task-012), [TASK-013](../planning/tasks/10_Jira_Backlog.md#task-013), [TASK-038](../planning/tasks/10_Jira_Backlog.md#task-038).

Автентифікація перевіряє особу. Авторизація перевіряє, що їй дозволено зробити. Для кожної операції окремо перевіряємо дію, доступні записи та дозволені поля.

| Роль | Доступ |
|---|---|
| `ADMIN` — адміністратор | Управління всіма областями, рахунками користувачів і ролями; фінанси, повернення та аудит |
| `MANAGER` — менеджер | Операційне управління людьми, дітьми, групами, харчовими даними й розкладом; рахунки та підтвердження оплат; без зарплат, фінансових сценаріїв, ролей і повернень |
| `PARENT` — законний представник | Власний профіль; свої діти, їхні харчові дані, пільги, рахунки й платежі; опублікований розклад їхніх груп |
| `TEACHER` — викладач | Власні заняття, мінімальні дані відповідних груп; зміна власної доступності та часу власного заняття в чернетці |
| `EDUCATOR` — вихователь | Мінімальні дані дітей і харчові обмеження призначеної групи, її розклад, власна доступність |
| `ASSISTANT` — помічник | Такий самий перегляд призначеної групи, як у вихователя, та власна доступність |

Представник може змінювати контакти власного профілю й харчові вподобання, алергії та виключені продукти своїх дітей. Не може змінювати представників, групу, статус, пільгу, фінансові суми чи підтверджувати оплату.

Вихователь і помічник читають харчові дані, але не редагують їх. Викладач не отримує персональні дані дітей, харчові обмеження, пільги або платежі через факт проведення заняття.

Менеджер може призначити дитині наявну пільгу, але не створює тарифи й фінансові правила. Профілі працівників повертаються йому без зарплат та облікових секретів.

Кілька ролей об’єднують дозволені дії. Розширені поля власної дитини доступні лише після перевірки зв’язку з цією дитиною. Роль `PARENT + EDUCATOR` не відкриває пільги чужих дітей своєї групи.

Ролі та дозволи визначені константами в коді. Адміністратор призначає лише відомі ролі. Працівницька роль потребує відповідної посади; роль не створює призначення в групу. Невідомі коди відхиляються, помилки конфігурації дозволів зупиняють запуск.

Законне представництво перевіряємо через зв’язок дитини з людиною. Доступ до рахунків мають усі поточні законні представники дитини, зокрема після її вибуття; вони бачать платежі без зайвих персональних даних інших платників. Ідентифікатор із запиту сам по собі не дає прав.

Для списків обмеження застосовуємо до пошуку, кількості та звітів до пагінації. Порожній перелік призначених груп означає відсутність записів. Прямий виклик сценарію без HTTP також перевіряє доступ.

## 6. Діти, представники та харчові дані

**Завдання:** [TASK-008](../planning/tasks/10_Jira_Backlog.md#task-008), [TASK-016](../planning/tasks/10_Jira_Backlog.md#task-016), [TASK-013](../planning/tasks/10_Jira_Backlog.md#task-013).

Дитина має ім’я, дату народження, статус, навчальний рік, вікову категорію, поточну групу, представників, інших родичів, харчові дані, пільгу та дати зарахування/вибуття. Контактні дані законних представників зберігаємо в `people`.

Представник — посилання на людину та вид зв’язку з дитиною. Для зарахування потрібен щонайменше один представник. До 4 представників і до 20 інших родичів на дитину. Інші родичі містять ім’я, зв’язок, контакти та примітку; автоматичного доступу до API не отримують.

Стани дитини:
- `APPLICANT` — заявка, місце не зайнято.
- `ACTIVE` — зарахована, місце зайнято.
- `SUSPENDED` — призупинена, місце збережено, нарахування тривають.
- `LEFT` — вибула, поточного місця немає, історія й фінансові зобов’язання збережені.

Переходи: заявка → зарахування; активна → пауза → відновлення; активна або призупинена → вибуття. Повторне зарахування вибулої дитини й поновлення закритого оплачуваного періоду відкладено. Помилки в персональних даних виправляє уповноважений працівник із аудитом.

Харчові дані: вподобання, виключені продукти, алергії та примітка. Це інформація для організації харчування, без діагнозів чи медичного обліку. Кухонний список доступний адміністратору, менеджеру та призначеному вихователю/помічнику.

Дата народження в майбутньому відхиляється. Збіг імені й дати народження дає попередження про можливий дубль, а не безумовну заборону створення.

## 7. Вік, навчальний рік, групи та кімнати

**Завдання:** [TASK-005](../planning/tasks/10_Jira_Backlog.md#task-005), [TASK-007](../planning/tasks/10_Jira_Backlog.md#task-007), [TASK-015](../planning/tasks/10_Jira_Backlog.md#task-015), [TASK-030](../planning/tasks/10_Jira_Backlog.md#task-030).

<a id="req-7-1"></a>

### 7.1. Вікова категорія

**Завдання:** [TASK-005](../planning/tasks/10_Jira_Backlog.md#task-005), [TASK-015](../planning/tasks/10_Jira_Backlog.md#task-015), [TASK-017](../planning/tasks/10_Jira_Backlog.md#task-017).

Початкові категорії — 2, 3, 4 і 5 років. Вік обчислюємо за календарною датою народження на 1 вересня навчального року, навіть якщо дитина поступає посеред року. Дитина іншого віку не зараховується, доки адміністратор не додасть відповідну категорію та її тарифи й програму.

Категорія не змінюється автоматично в день народження. Перехід у новий навчальний рік — явна операція переведення з перевіркою нового віку й місця. Група належить одному навчальному року; наступного року створюємо новий запис групи, зберігаючи старий для історії. Призначення кімнат і персоналу переключаємо атомарно; активні групи не ділять один ресурс.

<a id="req-7-2"></a>

### 7.2. Група

**Завдання:** [TASK-015](../planning/tasks/10_Jira_Backlog.md#task-015), [TASK-009](../planning/tasks/10_Jira_Backlog.md#task-009), [TASK-017](../planning/tasks/10_Jira_Backlog.md#task-017), [TASK-030](../planning/tasks/10_Jira_Backlog.md#task-030), [TASK-024](../planning/tasks/10_Jira_Backlog.md#task-024).

Поля групи: назва, навчальний рік, вікова категорія, місткість, базова кімната, вихователь, помічник, стан та технічний лічильник зайнятих місць.

Стани: `DRAFT` — неповна чернетка; `ACTIVE` — можна зараховувати; `INACTIVE` — нові зарахування заборонені. Деактивація допускається лише без дітей, які займають місця, та без несумісних майбутніх опублікованих занять. Порожня активна група продовжує використовувати кімнату й персонал.

Активація потребує доступної групової кімнати, вихователя та помічника відповідних посад. Місткість — 1–20 і не більше місткості кімнати. Один вихователь, помічник або кімната не можуть належати двом активним групам. Одну людину не призначаємо одночасно вихователем і помічником.

Група містить дітей лише однієї категорії. Список дітей отримуємо за `children.groupId`; масив дітей у групі не дублюємо. Зменшення місткості нижче зайнятих місць заборонене.

<a id="req-7-3"></a>

### 7.3. Кімнати

**Завдання:** [TASK-007](../planning/tasks/10_Jira_Backlog.md#task-007), [TASK-015](../planning/tasks/10_Jira_Backlog.md#task-015).

Кімната має код/номер, назву, тип, місткість та доступність. Початкові 5 службових кімнат: санвузол дітей, санвузол персоналу, менеджер, психолог, відпочинок персоналу. Вони не використовуються для групових занять.

Усі заняття групи відбуваються в її базовій кімнаті. Оренда належить будинку й зберігається як фінансове налаштування. Поле оренди кожної кімнати не створюємо. Адміністратор може додавати й замінювати кімнати; перша версія підтримує максимум 15 одночасно активних груп. Та сама межа діє для генератора й фінансового пошуку; подальше збільшення потребує перегляду бюджетів і перевірок.

<a id="req-8"></a>

## 8. Зарахування, переведення та вибуття

**Завдання:** [TASK-017](../planning/tasks/10_Jira_Backlog.md#task-017), [TASK-026](../planning/tasks/10_Jira_Backlog.md#task-026), [TASK-011](../planning/tasks/10_Jira_Backlog.md#task-011).

Операції виконуються адміністратором або менеджером і набувають чинності одразу. Час фіксує сервер. Клієнт не може переписати членство заднім числом чи запланувати його на майбутнє.

| Операція | Членство | Оплата |
|---|---|---|
| Зарахування заявки | Одразу займає місце в активній відповідній групі | Навчання й харчування з наступного місяця |
| Переведення | Одразу займає нове й звільняє старе місце | Початкова дата оплати зберігається; поточний місяць не перераховується |
| Пауза | Місце залишається | Нарахування продовжуються |
| Відновлення після паузи | Те саме місце | Без нового безоплатного періоду |
| Вибуття | Одразу звільняє місце | Поточний місяць зберігається; майбутні нарахування припиняються |

Зарахування перевіряє статус дитини, поточне членство, вік, навчальний рік, активність групи та вільне місце. Переведення має ті самі перевірки; невдала операція не змінює старої групи.

Зберігаємо початковий місяць оплати та перший місяць без оплати після вибуття. Оплачувані місяці утворюють інтервал із включеним початком і виключеним кінцем. Для переходу навчального року цей інтервал не починається заново.

Приклад: зарахування 15 жовтня → перші рахунки за листопад; вибуття 12 лютого → лютневі рахунки залишаються, з березня нових немає. Якщо дитина вибула до першого оплачуваного місяця, нарахувань немає. Денні перерахунки навчання й харчування не виконуються.

Для простежуваності зберігаємо компактні інтервали членства: група, початок, кінець. Поточний `groupId` визначає поточне членство. Історія не використовується для відновлення минулих зарплат. Початкова межа — 100 інтервалів на дитину; перевищення відхиляємо з поясненням, історію не обрізаємо.

Резервування/звільнення місць, зміна дитини, історія та аудит виконуються атомарно. Вибуття також скасовує ненадані майбутні частини рахунків через узгоджену операцію billing. Відправлення грошей назад є окремим підтвердженням адміністратора; до нього система показує суму до повернення.

<a id="req-9"></a>

## 9. Довідники, тарифи та пільги

**Завдання:** [TASK-007](../planning/tasks/10_Jira_Backlog.md#task-007), [TASK-018](../planning/tasks/10_Jira_Backlog.md#task-018).

У `catalog` зберігаємо види записів: вікові категорії, кімнати, дисципліни, посади, види пільг, тарифи навчання, тарифи харчування, робочі й фінансові налаштування. Кожний вид має власні перевірені поля. Довільний JSON від клієнта не допускається.

Тариф і фінансове правило мають дату початку дії. Зміни створюють нову версію; використані версії незмінні. На розрахункову дату обираємо останню версію, що вже діє. Однаковий код і дата початку версії не дублюються.

Нові фінансові версії починаються з першого числа наступного або пізнішого місяця. Датування в минулому не допускається. Відсутній тариф — явна помилка; непомітного використання нуля або іншої категорії немає.

Початковий тариф навчання — 15 000 грн/місяць. Денний тариф харчування: 300/400/500/600 грн для категорій 2/3/4/5 відповідно. Початкові пільги — 10%, 20%, 30%.

Дитина має одну чинну пільгу або не має пільги. Призначення містить вид пільги, зафіксований відсоток і календарний період дії. Майбутні призначення зберігаємо як невеликий датований перелік без перетинів; початкова межа — 100 записів. Зміна умов діє з наступного місяця, зберігає старі умови та аудит. Для нового зарахування можна одразу призначити пільгу з першого оплачуваного місяця.

Зміна довідника не змінює вже призначений відсоток, старі рахунки або оплачений рік. Тариф і пільга для місячного рахунку визначаються на перше число місяця послуг.

## 10. Гроші та правила округлення

**Завдання:** [TASK-004](../planning/tasks/10_Jira_Backlog.md#task-004).

Валюта — UAH. Суми зберігаємо цілими копійками: 15 000 грн = 1 500 000 копійок. Відсотки задаємо цілими базисними пунктами: 10% = 1000, 12% = 1200, 100% = 10000.

Грошовий результат округлюється до копійки за правилом «половина вгору». Проміжні процентні множення виконуються точно, наприклад через `BigInt`; у базу й JSON повертаємо безпечні цілі числа. Перевіряємо діапазони, знак і переповнення.

Один набір чистих функцій округлення й знижок використовується billing та finance. Календарні функції також спільні. Не створюємо складний універсальний фінансовий фреймворк.

## 11. Рахунки за навчання та харчування

**Завдання:** [TASK-019](../planning/tasks/10_Jira_Backlog.md#task-019), [TASK-025](../planning/tasks/10_Jira_Backlog.md#task-025), [TASK-026](../planning/tasks/10_Jira_Backlog.md#task-026), [TASK-031](../planning/tasks/10_Jira_Backlog.md#task-031).

<a id="req-11-1"></a>

### 11.1. Рахунок

**Завдання:** [TASK-019](../planning/tasks/10_Jira_Backlog.md#task-019), [TASK-025](../planning/tasks/10_Jira_Backlog.md#task-025).

Рахунок `invoice` описує зобов’язання, платіж `payment` — рух грошей. Типи послуг: `TUITION` — навчання та `MEAL` — харчування. Один платіж стосується одного рахунку й однієї дитини.

Рахунок містить дитину, тип, період, дату створення, строк оплати, початкову суму, тариф, пільгу, формулу, місячні частини та інформацію про оплату й скасування. Це незмінний знімок умов із окремими дозволеними змінами стану.

Для кожної дитини, типу послуги й місяця існує не більше одного чинного резервування нарахування. Річний рахунок резервує 12 місяців навчання; місячні рахунки з ним не перетинаються. Скасування звільняє тільки скасовані місяці; старі записи залишаються.

Команди формування рахунків запускаємо явно, без фонового планувальника. Місячні рахунки створюємо за поточний оплачуваний місяць. Пропущений минулий місяць не відновлюємо автоматично; це явне обмеження, яке показуємо адміністратору. Річний рахунок можна підготувати на наступний оплачуваний місяць.

<a id="req-11-2"></a>

### 11.2. Місячне навчання

**Завдання:** [TASK-019](../planning/tasks/10_Jira_Backlog.md#task-019).

Сума = тариф місяця після персональної пільги з округленням до копійки. Часткові оплати дозволені. Початковий строк — до кінця 10-го календарного дня місяця послуг у Europe/Kyiv. Якщо рахунок створено пізніше, він може одразу бути простроченим; це відображається явно.

<a id="req-11-3"></a>

### 11.3. Харчування

**Завдання:** [TASK-019](../planning/tasks/10_Jira_Backlog.md#task-019).

Сума = денний тариф вікової категорії × число понеділків–п’ятниць у місяці. Ті самі межі оплачуваного періоду й строк оплати, що в місячного навчання. Пільга навчання та річна знижка не застосовуються. Свята, пропуски та вибуття посеред місяця не зменшують рахунок.

<a id="req-11-4"></a>

### 11.4. Річне навчання

**Завдання:** [TASK-025](../planning/tasks/10_Jira_Backlog.md#task-025).

Річний рахунок охоплює 12 послідовних місяців, незалежно від меж навчального року. Тариф і пільга беруться на перше число першого місяця послуг і фіксуються на весь рік.

Формула:

```text
сума після пільги = round(місячний тариф × 12 × (1 − персональна пільга))
річна сума = round(сума після пільги × 0,88)
```

Приклад: 15 000 × 12 × 0,90 × 0,88 = 142 560 грн. Знижки застосовуються послідовно, не як 10% + 12%.

Суму в копійках ділимо на 12; залишок по одній копійці додаємо першим місяцям. Сума місячних частин точно дорівнює рахунку. Харчування продовжує виставлятися помісячно.

Річний рахунок приймає один повний підтверджений платіж до кінця дня перед першим місяцем послуг. Часткове підтвердження заборонене. Дата фактичного надходження й підтвердження мають бути до цієї межі; пізнє підтвердження не активує прострочений річний рахунок.

До повної своєчасної оплати річний рахунок не додає доходу послуг. При пропуску строку явна ідемпотентна команда переходу на місячну оплату скасовує неоплачений річний рахунок і формує рахунок поточного місяця. Поки команду не виконано, система показує потребу в переході й не дублює резервування. Автоматичного cron немає.

<a id="req-11-5"></a>

### 11.5. Оплата, скасування та сума до повернення

**Завдання:** [TASK-021](../planning/tasks/10_Jira_Backlog.md#task-021), [TASK-026](../planning/tasks/10_Jira_Backlog.md#task-026), [TASK-027](../planning/tasks/10_Jira_Backlog.md#task-027), [TASK-031](../planning/tasks/10_Jira_Backlog.md#task-031).

Відокремлюємо стан послуг від стану оплати. `UNPAID`, `PARTIALLY_PAID`, `PAID` — результати співвідношення чинних зобов’язань і чистої оплати. Прострочення визначає строк оплати; скасування послуг не означає оплату.

Початкова сума й суми місячних частин залишаються незмінними. Скасовані ненадані частини мають окремий стан та дату. Чинне зобов’язання дорівнює сумі нескасованих частин; чиста оплата — підтверджені надходження мінус підтверджені повернення.

```text
неоплачений залишок = max(0, чинне зобов’язання − чиста оплата)
сума до повернення = max(0, чиста оплата − чинне зобов’язання)
```

Другий результат виникає після дозволеного скасування вже оплаченої майбутньої послуги; це не переплата, дозволена при прийманні платежу. Обидві суми показуємо окремо, без від’ємного боргу.

При вибутті річні частини від наступного місяця скасовуються. Минулі та поточний місяці не перераховуються; річну знижку заднім числом не забираємо. Повернення не створює нового боргу за скасовані частини.

Приклад: річний рахунок 142 560 грн має 12 частин по 11 880 грн і повністю оплачений. Після трьох оплачуваних місяців дитина вибуває, наступні дев’ять частин скасовуються. Чинне зобов’язання — 35 640 грн, сума до повернення — 106 920 грн. Після підтвердженого повернення чиста оплата — 35 640 грн; і неоплачений залишок, і сума до повернення дорівнюють нулю. Первинне надходження та всі початкові суми залишаються в історії.

Скасування вже наданих місяців, довільна зміна сум і звичайний DELETE фінансових документів заборонені. Адміністратор скасовує ненадані послуги; менеджер оформлює вибуття, а пов’язане скасування наступних місяців виконується як частина цього сценарію.

<a id="req-12"></a>

## 12. Платежі та повернення

**Завдання:** [TASK-020](../planning/tasks/10_Jira_Backlog.md#task-020), [TASK-021](../planning/tasks/10_Jira_Backlog.md#task-021), [TASK-027](../planning/tasks/10_Jira_Backlog.md#task-027).

Представник створює повідомлення про оплату зі станом `PENDING`. Це не надходження. Способи: `BANK_TRANSFER` — переказ і `CASH` — готівка. Зберігаємо суму, рахунок, автора/платника та необов’язковий зовнішній номер чи коментар. Карткові реквізити не збираємо.

Для представника платника визначає сервер. Для працівника, що реєструє оплату від імені представника, сервер перевіряє його зв’язок із дитиною та окремо зберігає автора операції. Клієнт не може підставити неперевіреного платника.

Менеджер або адміністратор підтверджує чи відхиляє повідомлення. Підтвердження перевіряє чинність рахунку та залишок. Надходження понад чинне зобов’язання заборонене, навіть якщо паралельно надходять кілька запитів.

Платіж зберігає `occurredAt` — фактичну дату грошей і `confirmedAt` — дату підтвердження системою. Працівник підтверджує фактичну дату, яка не може бути в майбутньому. Надходження за минулі дати допускаються як пізно зареєстровані факти; це не дає права переписувати зарахування чи створювати зарплату за минулий місяць.

Після підтвердження суму, напрямок, рахунок і дату надходження не редагуємо. Повернення — окрема операція `REFUND`, прив’язана до первинного підтвердженого надходження `RECEIPT`.

Повернення виконує лише адміністратор після скасування ненаданих послуг. Сума не перевищує ні поточну суму до повернення за рахунком, ні неповернену частину первинного надходження. Якщо надходжень кілька, можна виконати кілька повернень із явними посиланнями. Кілька конкурентних запитів не можуть повернути більше дозволеного.

Ідемпотентність означає: повтор із тим самим ключем і даними дає попередній результат, інші дані з тим самим ключем — конфлікт. Це правило діє для створення платежів і повернень. Повтор підтвердження не збільшує оплату вдруге.

Зміна стану платежу, підсумків рахунку та аудит — одна транзакція. Повідомлення, що очікують, і відхилені повідомлення у фінансові надходження не входять.

<a id="req-13"></a>

## 13. Витрати, відкриття місяця та зарплати

**Завдання:** [TASK-028](../planning/tasks/10_Jira_Backlog.md#task-028), [TASK-029](../planning/tasks/10_Jira_Backlog.md#task-029).

<a id="req-13-1"></a>

### 13.1. Витрата

**Завдання:** [TASK-028](../planning/tasks/10_Jira_Backlog.md#task-028).

Витрата має категорію, місяць, суму, стан, знімок розрахунку, автора та за потреби дату оплати. Категорії: оренда, зарплата, харчування, інші. Стани: `DRAFT` — підготовлена; `APPROVED` — затверджена; `CANCELLED` — скасована до затвердження.

Затвердження й оплата — різні факти. У результат періоду входять затверджені витрати за місяцем послуг. У грошовий потік — оплачені за датою оплати. Часткову оплату витрати не реалізуємо: одна витрата має одну повну оплату, яку не проводимо повторно.

Оренда — одна витрата на будинок за місяць. Вартість їжі для батьків не є собівартістю закупівель; харчові витрати вводить адміністратор окремо.

<a id="req-13-2"></a>

### 13.2. Відкриття поточного зарплатного місяця

**Завдання:** [TASK-029](../planning/tasks/10_Jira_Backlog.md#task-029).

Адміністратор явно запускає команду відкриття поточного місяця. Вона формує чернетки оренди й зарплат на основі фактичного стану на момент першого запуску. Знімок містить дату, версії правил, працівників, посади, групи, кількість зайнятих місць і суми.

Це свідоме уточнення попередньої рекомендації «на перше число»: знімок 11 жовтня не називаємо станом на 1 жовтня. У звіті відображаємо його фактичну дату. Для стабільної роботи адміністратор відкриває місяць на початку, але система не вимагає непідтверджених історичних даних.

Команда доступна лише для поточного місяця; історичне відновлення відсутнє. Усі автоматичні рядки та ознаку відкриття записуємо атомарно. Ознака й дата знімка зберігаються в технічному записі `catalog`; окрема десята колекція не потрібна.

Повтор команди повертає ті самі рядки без перерахунку. `sourceKey` оренди — `rent:YYYY-MM`, зарплати — `salary:personId:YYYY-MM`. Якщо рядок скасовано, повтор не відновлює його непомітно. Одночасні відкриття не створюють дубль або різні знімки.

До знімка входять активні оплачувані працівники; вихователь і помічник — лише призначені активним групам. Відпустка/лікарняний не зменшують місячну зарплату навчальної моделі. Інші посади беруть фіксовану місячну суму з профілю й чинних правил. Увімкнений account чи роль не є підставою для зарплати.

<a id="req-13-3"></a>

### 13.3. Зарплатні правила

**Завдання:** [TASK-029](../planning/tasks/10_Jira_Backlog.md#task-029).

```text
n = кількість дітей, які займають місце у групі на дату знімка
додаткові діти = max(0, n − 12)
вихователь = 40 000 + 5 000 × додаткові діти
помічник = 20 000 + 3 000 × додаткові діти
пара = 60 000 + 8 000 × додаткові діти
```

За 20 дітей: вихователь 80 000, помічник 44 000, разом 124 000 грн. Порожня активна група має базову зарплату пари 60 000 грн. Діти зі збереженим місцем у `SUSPENDED` враховуються.

Початкові фіксовані зарплати: викладач — 40 000, менеджер — 80 000, психолог — 30 000, охоронець — 25 000, прибиральник — 25 000 грн. Усі параметри налаштовувані; 10 викладачів — тільки контрольний сценарій.

Після відкриття місяця зміни кількості дітей, призначень, штату й зарплатних умов не змінюють його автоматичні рядки. Новий знімок наступного місяця врахує актуальні дані. Операційна заміна вихователя або найм можуть діяти одразу; доплату за поточний місяць адміністратор оформлює окремою ручною витратою з причиною.

<a id="req-13-4"></a>

### 13.4. Виправлення й пропущені місяці

**Завдання:** [TASK-028](../planning/tasks/10_Jira_Backlog.md#task-028), [TASK-029](../planning/tasks/10_Jira_Backlog.md#task-029).

Чернетку можна скасувати й замінити ручним розрахунком із причиною; первинний знімок зберігається. Затверджений рядок не редагуємо. Коригування — окрема затверджувана витрата з посиланням на первинну, причиною та напрямком збільшення/зменшення. Сума коригування додатна, знак визначає напрямок.

Коригування не може знизити чисту суму вихідної витрати нижче нуля. Зменшення вже оплаченої витрати відкладено, оскільки потребувало б окремого обліку повернення від працівника або постачальника. Для оплаченої витрати дозволена лише додаткова доплата.

Якщо минулий місяць пропущено, автоматичні зарплати не відновлюємо. Адміністратор може створити ручну витрату за цей місяць із причиною й доказовими умовами. Звіт позначає відсутні автоматичні рядки та ручний характер розрахунку.

<a id="req-14"></a>

## 14. Дисципліни, програма та розклад

**Завдання:** [TASK-018](../planning/tasks/10_Jira_Backlog.md#task-018), [TASK-022](../planning/tasks/10_Jira_Backlog.md#task-022), [TASK-023](../planning/tasks/10_Jira_Backlog.md#task-023), [TASK-024](../planning/tasks/10_Jira_Backlog.md#task-024), [TASK-034](../planning/tasks/10_Jira_Backlog.md#task-034).

<a id="req-14-1"></a>

### 14.1. Програма

**Завдання:** [TASK-018](../planning/tasks/10_Jira_Backlog.md#task-018).

Початкові дисципліни: англійська, музика, фізкультура, вільна боротьба, шахи. Для кожної категорії задаємо кількість занять на тиждень і тривалість. Початково — 2 заняття кожної дисципліни на тиждень по 30 хвилин. Це навчальне припущення, а не педагогічна рекомендація.

Адміністратор може створювати дисципліни й змінювати програму для майбутніх тижнів. Групи однієї категорії отримують однакову програму. Викладач проводить лише свою дисципліну; кілька викладачів можуть покривати одну програму. Публікація зберігає використану версію програми; майбутня зміна не переписує минулі опубліковані тижні.

<a id="req-14-2"></a>

### 14.2. Тижневий розклад

**Завдання:** [TASK-022](../planning/tasks/10_Jira_Backlog.md#task-022), [TASK-023](../planning/tasks/10_Jira_Backlog.md#task-023), [TASK-024](../planning/tasks/10_Jira_Backlog.md#task-024).

Один документ розкладу охоплює весь садок за тиждень із понеділка. Робочі дні 09:00–17:00, часовий пояс Europe/Kyiv. Початкові щоденні блоки:

| Подія | Час |
|---|---|
| Сніданок | 09:30–10:00 |
| Обід | 12:00–12:30 |
| Сон | 13:00–14:00 |
| Підвечірок | 15:00–15:30 |

Три прийоми їжі не йдуть підряд. Час поза зайнятими блоками — вільна діяльність, яку можна обчислити без зберігання окремих порожніх слотів.

Заняття містить групу, дисципліну, викладача, базову кімнату, початок і кінець. Сітка та тривалості кратні 15 хвилинам. Інтервали `[start, end)` допускають сусідні заняття, але не перетини.

Перевіряємо: активність і навчальний рік групи, тип/місткість/доступність кімнати, посаду та дисципліну викладача, його доступність, робочий час, конфлікти групи/кімнати/викладача, сон і харчування, точну кількість обов’язкових занять. Вихователь і помічник мають бути доступними для роботи групи; їхня відсутність потребує відповідної заміни.

Чернетка має номер редакції `revision`. Збереження з застарілим номером повертає конфлікт і не перезаписує чужі зміни. Адміністратор і менеджер редагують чернетку та публікують її. Викладач змінює лише час власного заняття; групу, кімнату, дисципліну й викладача не підміняє.

Публікація повторно перевіряє актуальні ресурси та весь тиждень. Зберігаємо останній опублікований знімок окремо від чернетки. Батьки бачать його, поки нова редакція не опублікована. Якщо публікації ще немає, повертаємо явний порожній результат, без доступу до чернетки.

Зміна ресурсу, доступності чи програми не може зробити майбутній опублікований тиждень невалідним. Несумісну зміну відхиляємо; спочатку потрібно підготувати узгоджену заміну через спільний сценарій зміни ресурсів і перепублікації. Цей сценарій змінює ресурси та потрібні опубліковані тижні однією транзакцією. Для першої версії публікуємо не далі ніж на 4 тижні вперед, щоб обсяг такої операції був обмежений.

<a id="req-14-3"></a>

### 14.3. Генератор

**Завдання:** [TASK-034](../planning/tasks/10_Jira_Backlog.md#task-034).

Генератор отримує знімок даних, спочатку ставить сон і харчування, потім розміщує заняття найбільш обмежених дисциплін. Вибирає менш завантажених викладачів і дні, зберігає детермінований порядок для однакових входів.

Результат: чернетка, незаплановані заняття та причини. Не публікує самостійно. Неповний результат можна вручну виправити, але опублікувати неповну програму не можна.

Початкові межі: 15 груп, 2000 слотів на тиждень, 100 000 перевірок кандидатного розміщення й 2 секунди пошуку. Межі задаємо перевіреною конфігурацією. Бюджет перевіряємо всередині циклу; між обмеженими порціями роботи передаємо керування циклу подій. Один таймер або слово `async` не є захистом довгого синхронного перебору.

Невдача евристики означає, що алгоритм не знайшов розклад у своїх межах. Це не доказ математичної неможливості. За перевищення ліміту повертаємо неповний результат із поясненням.

## 15. Звіти та фінансові показники

**Завдання:** [TASK-010](../planning/tasks/10_Jira_Backlog.md#task-010), [TASK-030](../planning/tasks/10_Jira_Backlog.md#task-030), [TASK-031](../planning/tasks/10_Jira_Backlog.md#task-031), [TASK-032](../planning/tasks/10_Jira_Backlog.md#task-032), [TASK-033](../planning/tasks/10_Jira_Backlog.md#task-033).

Усі фактичні звіти будуються з MongoDB через aggregation-адаптери. Сценарій перевіряє роль, область і період, а база групує дозволені дані. Порожні групи не зникають зі звіту наповненості. Дані персоналу й фінанси не розкриваються через загальний звіт.

Обов’язкові звіти:

- Поточна наповненість груп, вільні місця та порівняння лічильника зі зв’язками дітей.
- Поточні рахунки, неоплачені залишки та прострочення.
- Дохід послуг і надходження/повернення за місяцями.
- Затверджені витрати за категоріями, зарплатний фонд, оренда.
- Фінансовий результат і грошовий потік.
- Поточний розподіл пільг.
- Навантаження викладачів за опублікованими заняттями.

| Показник | Правило |
|---|---|
| Нарахований дохід місяця | Чинні місячні частини рахунків за послуги цього місяця; оплачений рік розподілений на 12 частин |
| Чисті надходження місяця | Підтверджені надходження мінус підтверджені повернення за фактичною датою грошей |
| Витрати місяця | Затверджені витрати та їхні допустимі коригування за місяцем послуг |
| Результат місяця | Нарахований дохід мінус витрати місяця |
| Грошовий потік місяця | Чисті надходження мінус фактично оплачені витрати за датою оплати |
| Поточний неоплачений залишок | Сума додатних залишків чинних рахунків зараз |
| Поточна прострочена сума | Частина поточного залишку, строк оплати якої минув |
| Поточна сума до повернення | Підтверджені гроші понад зобов’язання після дозволеного скасування майбутніх послуг |

Місяць для фактичного результату не може бути в майбутньому. Для поточного місяця результат є попереднім: містить нарахування за місяць і зареєстровані на цей момент факти. Майбутні оцінки подаються окремо як прогноз.

Неоплачений річний рахунок до строку оплати показує зобов’язання, але не дохід місяця послуг. Прострочений річний рахунок очікує переходу на місячну оплату й не перетворюється на дохід.

Історичну заборгованість на кінець вибраного місяця не реалізуємо. У відповіді місячного звіту поточні поля мають назви `currentOutstandingMinor`, `currentOverdueMinor`, `currentRefundDueMinor` та час `asOf`. Панель підписує їх як стан зараз. Старе поле `outstandingMinor` із значенням боргу на кінець місяця не використовуємо.

Основні місячні поля: `month`, `accruedIncomeMinor`, `receiptsNetMinor`, `expensesMinor`, `resultMinor`, `cashFlowMinor`, `expenseBreakdown`, `notes`. Нотатки пояснюють пропущені витрати, незатверджені зарплати, пізні підтвердження та межі навчальної моделі.

Пізніше підтвердження фактичного надходження або ручної витрати може змінити звіт за минулий місяць. Закриття бухгалтерських періодів, незмінні історичні звіти та відновлення стану всіх документів на минулу дату відкладені.

Не додаємо суми рахунків після з’єднання з багатьма платежами без контролю дублювання рядків. Дохід, надходження й витрати можна агрегувати окремо та об’єднати в сценарії.

<a id="req-16"></a>

## 16. Прогноз, беззбитковість і порівняння сценаріїв

**Завдання:** [TASK-035](../planning/tasks/10_Jira_Backlog.md#task-035), [TASK-036](../planning/tasks/10_Jira_Backlog.md#task-036).

<a id="req-16-1"></a>

### 16.1. Межі моделі

**Завдання:** [TASK-035](../planning/tasks/10_Jira_Backlog.md#task-035).

Прогноз використовує явно передані тарифи, попит, персонал, кімнати, програми й частки знижок. Не змінює фактичні записи садка. Для стабільного місяця не враховує безоплатний залишок місяця зарахування; це припущення зазначаємо в результаті. Прогноз запуску з новими дітьми не видаємо за такий стабільний місяць.

Базовий фінансовий сценарій охоплює навчання, зарплати й оренду. Без собівартості харчування він називається результатом навчання до податків. За відсутності інших витрат повний прогноз позначаємо неповним; нуль не підставляємо непомітно.

Групи однієї категорії отримують рівномірно розподілених дітей із різницею не більше однієї дитини. Це фіксований спосіб розподілу пошуку, а не доказ найвигіднішого можливого розподілу. Різні вікові категорії не змішуємо.

<a id="req-16-2"></a>

### 16.2. Беззбитковість за фіксованих ресурсів

**Завдання:** [TASK-035](../planning/tasks/10_Jira_Backlog.md#task-035).

Вхід: кількість уже працюючих груп кожного віку, кімнати/місткість, фіксований штат викладачів та інших працівників, тарифи, витрати й частки знижок. Кожна активна група має базову зарплату навіть за нуль дітей.

Для одного віку перебираємо загальну кількість дітей від нуля до місткості й рівномірно розподіляємо між заданими групами. Для кількох вікових категорій потрібні граничний попит і частки кожної категорії. Сервер будує детерміновану послідовність: на кожному кроці додає дитину категорії з найбільшим відставанням від заданої частки серед тих, де ще є попит і місця; за рівності обирає менший вік. Перевіряємо всю цю послідовність, а не всі можливі розподіли за віками. Спосіб побудови й кінцевий розподіл повертаємо у відповіді.

Повертаємо мінімальну кількість дітей у перевіреній послідовності, за якої результат не від’ємний, кількість груп, розподіл і склад витрат. Межі гарантії явні: це поріг за заданих ресурсів і способу розподілу. Якщо в межах місткості такого результату немає, повертаємо пояснення. Фінансовий поріг не гарантує розклад: його здійсненність перевіряємо й позначаємо окремо.

<a id="req-16-3"></a>

### 16.3. Порівняння конфігурацій

**Завдання:** [TASK-036](../planning/tasks/10_Jira_Backlog.md#task-036).

Вхід: попит за категоріями, допустимий діапазон груп, доступні кімнати й межі кількості викладачів кожної дисципліни. Щоб уникнути прихованого відбору клієнтів, перша версія шукає конфігурацію, яка обслуговує весь заданий попит. Якщо ресурсів недостатньо, повертає нестачу; пошук прибутку шляхом відмови частині дітей відкладено.

Перебираємо до 15 груп загалом. Для кожної категорії визначаємо допустиму кількість непорожніх груп, рівномірно розподіляємо її попит, перевіряємо місткість і доступні кімнати. Вихователів та помічників потрібно по одному на групу. Порівнюємо задані варіанти штату викладачів; інші працівники та оренда задаються окремо.

Кандидат перевіряється тим самим генератором і валідатором розкладу, що фактична система, на переданих сценарних ресурсах. Штат сценарію може бути планованим, тому не потребує створення реальних `people`; доступність кожного сценарного викладача має бути задана.

Повертаємо:

- Найкращий знайдений сценарій із підтвердженим розкладом.
- Найменшу кількість груп серед перевірених конфігурацій, що обслуговують весь попит, мають не від’ємний результат і підтверджений розклад.
- Окремі кандидати, для яких розклад не підтверджений, і причини.
- Число перевірених варіантів, межі ресурсів, час, припущення та ознаку завершеності.

Початковий бюджет — 1000 кандидатів і 5 секунд на запит, зі спільним лімітом для вкладених запусків генератора. Не виконуємо 1000 незалежних пошуків по 2 секунди. Передаємо керування між порціями обчислень. При однакових результатах обираємо менше груп, потім менше викладачів, потім сталий порядок ідентифікаторів.

Термін «найкращий знайдений» обов’язковий навіть після повного перебору: спосіб розподілу фіксований, а генератор є евристикою. Відсутність підтвердженого розкладу не доводить неможливість.

## 17. Контрольний фінансовий приклад

**Завдання:** [TASK-004](../planning/tasks/10_Jira_Backlog.md#task-004), [TASK-010](../planning/tasks/10_Jira_Backlog.md#task-010), [TASK-029](../planning/tasks/10_Jira_Backlog.md#task-029), [TASK-035](../planning/tasks/10_Jira_Backlog.md#task-035).

Контрольна модель: 15 працюючих груп, 10 викладачів, 1 менеджер, психолог, охоронець і прибиральник. Оренда всього будинку — 50 000 грн. Навчання — 15 000 грн на дитину, без харчування.

Розподіл персональних пільг: 70% без пільги, 15% із 10%, 10% із 20%, 5% із 30%. Річну оплату обирають 20% клієнтів. Для цієї прогнозної таблиці вважаємо річну оплату й персональну пільгу незалежними.

```text
середній дохід = 15 000 × 0,95 × (0,80 + 0,20 × 0,88) = 13 908 грн
постійні витрати = 50 000 + 80 000 + 10 × 40 000 + 30 000 + 25 000 + 25 000
                = 610 000 грн
```

|---:|---:|---:|---:|---:|---:|
| 10 | 150 | 2 086 200 | 900 000 | 610 000 | 576 200 |
| 12 | 180 | 2 503 440 | 900 000 | 610 000 | 993 440 |
| 14 | 210 | 2 920 680 | 1 140 000 | 610 000 | 1 170 680 |

| 18 | 270 | 3 755 160 | 1 620 000 | 610 000 | 1 525 160 |

Усі суми таблиці у гривнях. Це очікуваний дохід стабільного місяця, а не сума банківських платежів за місяць. За фіксованих 15 активних груп фінансовий поріг без надбавок — 109 дітей при розподілі не більше 12 у кожній групі: 108 дітей дають −7 936 грн, 109 — +5 972 грн. ## 18. Історія, редагування та видалення

**Завдання:** [TASK-011](../planning/tasks/10_Jira_Backlog.md#task-011), [TASK-013](../planning/tasks/10_Jira_Backlog.md#task-013), [TASK-026](../planning/tasks/10_Jira_Backlog.md#task-026), [TASK-028](../planning/tasks/10_Jira_Backlog.md#task-028).

| Ресурс | Дозволені зміни та завершення |
|---|---|
| Людина | Редагування дозволених полів; деактивація, блокування account; видалення тільки без будь-яких посилань чи історії |

| Кімната та дисципліна | Редагування з перевіркою залежностей; використану деактивуємо, не видаляємо |
| Тариф і фінансове правило | Нова версія, без зміни використаного знімка |
| Пільга | Нове датоване призначення; старі рахунки незмінні |
| Розклад | Чернетка та нова публікація; історія змін у аудиті, остання публікація збережена |
| Рахунок і платіж | Явні фінансові команди; фізичне видалення та довільний PATCH сум відсутні |
| Витрата | Чернетка, затвердження, оплата, дозволене коригування; затверджений знімок незмінний |

### 19.3. Структура коду та зв’язки

**Завдання:** [TASK-001](../planning/tasks/10_Jira_Backlog.md#task-001), [TASK-040](../planning/tasks/10_Jira_Backlog.md#task-040).

За рішенням команди від 12 жовтня 2026 року використовуємо плоскі модулі без папок domain/application/infrastructure/presentation:

- routes: адреси й порядок middleware;
- controller: HTTP-вхід, виклик service та DTO відповіді;
- schema: Zod-контракти вхідних даних та публічних відповідей;
- openapi: опис HTTP-операцій із використанням цих схем;
- service: бізнес-правила, права, політики та організація атомарних дій;
- repository: MongoDB-запити, індекси, aggregation, перетворення ObjectId;
- model: структура документа Mongoose;
- dto: явно дозволені публічні поля;
- constants: стани, обмеження та коди;
- module: складання DI через конструктори.

Спільні налаштування лежать у config, HTTP-обробники у middleware, технічна телеметрія у telemetry, невеликі утиліти у utils. Service отримує repository ззовні й не імпортує Mongoose. Repository повертає звичайні об’єкти зі строковими ID; Mongoose-документи, ObjectId і session залишаються всередині нього.

Технічне оновлення 12 жовтня: OpenAPI генерується зі схем Zod та описів операцій модулів, збирач лежить у src/openapi. docs/api/openapi.json — лише експорт, сервер його не читає. Призначення, відповіді й права операцій описуємо явно; генерація не замінює валідацію та авторизацію. Інструкція — [11_OpenAPI_Generation.md](../development/11_OpenAPI_Generation.md).

Шлях запиту: маршрути та ранні перевірки → Zod → controller → service з бізнес-перевірками → repository → DTO. Перевірка доступу в service обов’язкова незалежно від middleware.

Модуль змінює власні колекції. Для іншого модуля використовує його service. Складні міжмодульні workflows за потреби лежатимуть у src/workflows, без циклів. Звіти можуть виконувати погоджений read-only $lookup у чужі колекції. Докладна чинна структура — docs/architecture/02_Architecture_Decisions.md.

### Локальне спостереження під час розробки

За рішенням користувача від 11 жовтня 2026 року до допоміжних інструментів додано OpenTelemetry та локальний Jaeger. За останнім рішенням користувача вони показують тільки HTTP-запит; ручні обгортки service/repository прибрані. Стандартний режим експортує технічні атрибути й безпечні коди помилок. За наступним рішенням користувача dev-режим може показувати JSON запиту/відповіді й бізнес-ID; секретні поля маскуються. Цей показ вимкнений у production та test. Ручну карту файлів у спанах скасовано за наступним рішенням користувача; орієнтуємося на назви операцій. Недоступність Jaeger не скасовує бізнес-операцію. Телеметрія не є бізнес-аудитом і не змінює перелік дев’яти колекцій. Запуск та межі описані в [05_Local_Telemetry.md](../development/05_Local_Telemetry.md).

### 19.4. Конкурентність

**Завдання:** [TASK-011](../planning/tasks/10_Jira_Backlog.md#task-011), [TASK-013](../planning/tasks/10_Jira_Backlog.md#task-013), [TASK-015](../planning/tasks/10_Jira_Backlog.md#task-015), [TASK-017](../planning/tasks/10_Jira_Backlog.md#task-017), [TASK-021](../planning/tasks/10_Jira_Backlog.md#task-021), [TASK-024](../planning/tasks/10_Jira_Backlog.md#task-024), [TASK-025](../planning/tasks/10_Jira_Backlog.md#task-025), [TASK-027](../planning/tasks/10_Jira_Backlog.md#task-027), [TASK-029](../planning/tasks/10_Jira_Backlog.md#task-029).

Зарахування умовно збільшує лічильник тільки якщо група активна й місце є. Переведення, фінанси, критичні призначення й аудит використовують транзакції. MongoDB працює як локальний replica set, достатньо одного вузла.

Унікальні індекси захищають email account, активні ресурси груп, код/версію довідника, тиждень розкладу, місяці рахунку, ключі платежів і автоматичних витрат. Для людини одночасні різні призначення також перевіряються під спільною серіалізацією ресурсів; окремий індекс вихователя не захищає від призначення тієї ж людини помічником в іншому запиті.

Публікація й зміни ресурсів використовують спільний транзакційний guard — технічний запис із ревізією в catalog. Захист останнього адміністратора має окремий guard. Ці записи змінювані й не є незмінними фінансовими версіями налаштувань.

`UnitOfWork` — невеликий механізм виконання операцій однією транзакцією — передає адаптери з однаковою session. Усередині транзакції операції послідовні, без `Promise.all`, зовнішніх HTTP-викликів і сторонніх ефектів при повторі. Помилка аудиту відкочує критичну зміну.

## 20. API, безпека та робота з датами

**Завдання:** [TASK-003](../planning/tasks/10_Jira_Backlog.md#task-003), [TASK-005](../planning/tasks/10_Jira_Backlog.md#task-005), [TASK-009](../planning/tasks/10_Jira_Backlog.md#task-009), [TASK-012](../planning/tasks/10_Jira_Backlog.md#task-012), [TASK-013](../planning/tasks/10_Jira_Backlog.md#task-013), [TASK-023](../planning/tasks/10_Jira_Backlog.md#task-023), [TASK-038](../planning/tasks/10_Jira_Backlog.md#task-038).

Префікс API — `/api/v1`. Список повертає `{data, meta:{page,limit,total}}`, один ресурс — `{data}`. Початковий limit — 20, максимум — 100. Фільтри, сортування й поля оновлення визначені явно.

Zod перевіряє body/query/params, невідомі поля відхиляються. Не передаємо клієнтські об’єкти безпосередньо в MongoDB-фільтри чи update. Клієнт не керує ролями поза спеціальною операцією, хешем пароля, внутрішніми лічильниками чи фактом підтвердження грошей.

Дати народження — календарні рядки, місяці — `YYYY-MM`, навчальний рік — погоджений код на кшталт `2026-2027`. Події зберігаємо як UTC timestamps. Межі періодів і локальні години обчислюємо в Europe/Kyiv із переходами часу; постійний зсув +2/+3 не використовуємо.

Помилки мають `code`, `message`, необов’язкові безпечні `details` і `requestId`. Статуси: 400 — некоректний запит; 401 — немає чинної автентифікації; 403 — немає дозволу; 404 — запис відсутній або недоступний; 409 — конфлікт стану/версії/унікальності; 413 — завелике тіло; 422 — бізнес-правило; 429 — ліміт; 500 — непередбачена помилка без технічних секретів.

Access JWT діє 30 хвилин; перевіряємо підпис, явно дозволений алгоритм, видавця, одержувача й строк. На захищеному запиті читаємо актуальні `enabled`, `roles`, `tokenVersion` із бази. Блокування й нові ролі діють на наступному запиті. Refresh token немає; після завершення строку потрібен новий вхід. Зміна пароля та logout-all відкликають попередні токени.

Паролі хешуємо; для bcrypt обмежуємо довжину 72 байтами UTF-8. Початковий адміністратор отримує пароль із env. Останнього активного адміністратора не можна заблокувати, видалити чи позбавити ролі, навіть конкурентними запитами.

Початковий HTTP-захист: Helmet; 300 запитів/IP за хвилину для всіх адрес; 30 операцій запису/IP за хвилину для `/api/v1`; JSON звичайного запиту до 32 КБ; заголовки до 10 секунд; запит до 30 секунд; бездіяльність сокета до 30 секунд; keep-alive 5 секунд. Ліміти стоять до JSON-парсера. Login має окремі 10 спроб/IP за 15 хвилин. Відповідь 429 містить час очікування. Лічильники в пам’яті одного процесу й скидаються при перезапуску.

Для повної чернетки тижневого розкладу передбачаємо окремий ліміт JSON до 512 КБ: 32 КБ може бути недостатньо навіть для 15 груп. Виняток діє тільки для відповідної команди після перевірки автентифікації й дозволу; обмеження кількості слотів і полів також діють. Невідомі поля, перевищення байтової межі або 2000 слотів відхиляються. Загальний парсер на 32 КБ не повинен перехоплювати цей маршрут перед його спеціальним парсером. Це майбутня зміна етапу scheduling, а не вже реалізована функція 0.3.0.

Налаштування перевіряємо при запуску. Для прямого локального з’єднання `trust proxy=false`. Локальний HTTP не примушуємо до HTTPS через HSTS. CORS для панелі дозволяє лише точний налаштований локальний origin у development, GET, Authorization і потрібний OPTIONS. Авторизацію для панелі не вимикаємо.

HTTP-тайм-аути не скасовують бізнес-операції й не обмежують CPU-перебір. Транспортні помилки Node.js можуть мати власний формат. Захист навчального сервера не є гарантією протидії DDoS.

Логи містять requestId, метод, шлях, статус і тривалість; не містять паролів, токенів, Authorization та харчових персональних даних. Усі зміни критичних даних доступні в аудиті адміністратору.

## 21. Допоміжна панель

**Завдання:** [TASK-037](../planning/tasks/10_Jira_Backlog.md#task-037).

Панель — окремий інструмент для локальної демонстрації, не частина backend і не кабінет батьків. Має демонстраційний режим із вигаданими даними та API-режим адміністратора. Виконує лише читання; бізнес-формули не дублює.

Токен зберігається тільки в пам’яті вкладки. У журналах і JSON-перегляді немає секретів. Для API-режиму секції мають явні стани: завантажено, ще не реалізовано, помилка, застарілі дані. Помилка не підміняється демонстраційними цифрами.

Панель підтримує пагінацію, 401, 429, тайм-аут і зміну місяця. У фінансах розрізняє показники вибраного місяця та поточні борги з датою `asOf`. Кожна секція оновлюється узгодженим набором даних; частково завантажений набір не показуємо як повний.

## 22. Якість коду та порядок реалізації

**Завдання:** [TASK-001](../planning/tasks/10_Jira_Backlog.md#task-001), [TASK-002](../planning/tasks/10_Jira_Backlog.md#task-002), [TASK-040](../planning/tasks/10_Jira_Backlog.md#task-040).

Код, який пише команда, має бути пояснюваним. Використовуємо зрозумілі назви, короткі функції, явні залежності, прості чисті розрахунки та вузькі методи репозиторіїв. Коментар пояснює причину чи нетривіальне правило. Документи й коментарі українською, технічні ідентифікатори англійською.

Не створюємо заздалегідь порожні папки й десятки класів. Не використовуємо спадкування тільки заради шаблону, `BaseService`, `BaseController`, універсальний CRUD-конструктор, service locator чи власний великий транзакційний фреймворк. Повторювані стани й коди визначаємо константами, але одноразовий текст не перетворюємо на абстракцію.

Послідовність інтеграції:

1. Узгоджені документи, запуск, стиль, поточний HTTP-захист та OpenAPI.
2. MongoDB, реальний репозиторій груп, тестова база, гроші й календар.
3. Catalog, транзакції та аудит.
4. Люди, вхід, ролі й захист маршрутів.
5. Групи, ресурси, діти та безпечне членство.
6. Місячні рахунки, оплата й відкриття зарплатного місяця; ручний розклад можна виконувати паралельно після узгодження контрактів.
7. Річна оплата, скасування, повернення та aggregation-звіти.
8. Генератор, фінансові сценарії й підключення панелі.
9. Інтеграційна перевірка й демонстрація.

Тести та OpenAPI оновлюємо з кожним сценарієм. Не оголошуємо етап завершеним тільки через наявність файлів. Пропущену залежність не підміняємо прихованою демонстрацією в робочому режимі.

## 23. Запуск і перевірки

**Завдання:** [TASK-002](../planning/tasks/10_Jira_Backlog.md#task-002), [TASK-003](../planning/tasks/10_Jira_Backlog.md#task-003), [TASK-039](../planning/tasks/10_Jira_Backlog.md#task-039), [TASK-040](../planning/tasks/10_Jira_Backlog.md#task-040).

Node.js запускається локально, MongoDB — у Docker Compose як replica set з volume. Backend-контейнер необов’язковий. API починає приймати запити після успішного підключення БД. Автоматичного fallback у пам’ять при помилці MongoDB немає.

Seed — початкове заповнення — та створення індексів ідемпотентні. При повторі seed не дублює дані й не переписує чинні тарифи чи людей. Демонстраційні дані вигадані; секретів у Git немає. Якщо потрібне очищення демобази, це окрема явно названа команда.

README описує встановлення, env, MongoDB, seed, індекси, запуск і тести. `/health/live` перевіряє процес, `/health/ready` — готовність БД. SIGINT/SIGTERM зупиняють приймання запитів і закривають з’єднання.

Unit-тести перевіряють чисті правила; HTTP-тести — контракти й доступ; інтеграційні тести на реальному replica set — індекси та транзакції. Тестова база окрема, команди очищення відмовляються працювати з базою розробки. CI — автоматична перевірка змін — запускає встановлення, стиль, тести й тестову MongoDB.
