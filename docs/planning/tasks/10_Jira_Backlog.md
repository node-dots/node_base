# Командний backlog у форматі Jira

Оновлено 13 жовтня 2026 року · чернетка постановок · українська мова.

Спочатку прочитайте [план командної розробки](../plans/09_Team_Delivery_Plan.md). Джерело бізнес-правил — [узгоджені вимоги v2.1](../../requirements/00_Consolidated_Requirements.md); структура коду — [архітектурні рішення](../../architecture/02_Architecture_Decisions.md).

У кожній картці поле **«Вимоги»** веде до відповідних розділів ТЗ; у ТЗ є зворотні TASK-посилання. Для розуміння міжмодульної операції прочитайте [бізнес-ланцюжки](../../architecture/12_Business_Flows.md). Посилання означає покриття постановкою, а не статус Done.

## Як перенести в Jira

EPIC-01–07 та TASK-001–040 — локальні посилання цього документа, не справжні Jira keys. Створіть сім Epic, потім потрібні Story/Task; Summary — назва картки, Description — її зміст, Assignee/Reviewer — реальні імена S1–S8, Parent — відповідний Epic. Поле Blocked by перетворіть на зв’язки `is blocked by`, локальні ID замініть Jira keys. Sub-task додавайте після уточнення великої картки; залежності між сценаріями мають залишитися видимими на рівні батьківських задач.

Усі картки зараз **Backlog**. TASK-001 — перша спільна робота. Після неї перша порція: TASK-002, TASK-004–010. TASK-003 вже реалізована локально; S1 після TASK-002 інтегрує та перевіряє готовий результат у спільному Git/CI, не пише endpoint заново. Доки Git не готовий, дозволені локальна підготовка й узгодження; спільне злиття коду потребує TASK-002. Обираємо рівно одну активну задачу на учасника.

TASK-001–012 описують найближчу підготовку. Решта — черга сценаріїв для refinement: перед Ready уточнити endpoint, request/response, помилки, індекси, тестові приклади та необхідні підзадачі. L не видається студенту одним великим PR. Не копіюйте весь backlog у поточний спринт.

Розмір — орієнтир складності, не дедлайн: **S** — один локальний результат; **M** — невеликий сценарій із кількома перевірками; **L** — потребує розбиття й часто парної роботи. Години/story points команда оцінює після обговорення й перших завершених задач. Пріоритет команди — число 1–10: 10 означає найвищий пріоритет. 10 — основа, гроші та ключові guards; 8–9 — основні бізнес-сценарії й перевірки; 5–7 — наступні обчислення та звіти; 1–4 — пізні можливості. Задача береться тільки з виконаними залежностями. Дати й оцінки — попередній розрахунок у [Ганті](../gantt/13_Gantt_Plan.md); для 10 годин на тиждень на учасника. У Jira це можна зберігати як окреме числове поле «Пріоритет команди», не плутати зі статусом і severity дефекту.

**Для кожної картки обов’язкові:** Definition of Done з плану; українські docs/коментарі, явний constructor DI, безпечні DTO, актуальний OpenAPI для зміненого API, політики service та відповідні негативні тести. Власник вказаний як пропозиція. При зміні правил спочатку оновити вимоги. Відповіді й схеми не визначати самостійно всупереч контракту споживача.

**Перевірка/демонстрація:** Команда проходить приклад JSON через шари; два учасники незалежно описують той самий вхід і вихід.

**Межі:** Не визначати весь API наперед і не створювати порожні модулі.

### TASK-002 · Налаштувати спільний Git-процес та CI

**Вимоги:** [§ 19.1 · Стек](../../requirements/00_Consolidated_Requirements.md#req-19-1); [§ 22 · Якість коду та порядок реалізації](../../requirements/00_Consolidated_Requirements.md#req-22); [§ 23 · Запуск і перевірки](../../requirements/00_Consolidated_Requirements.md#req-23).

**Тип:** Task · **Epic:** EPIC-01 · **Пріоритет:** 10/10 · **Розмір:** M  
**Власник:** S1 · **Reviewer:** S4 · **Blocked by:** TASK-001  
**Labels:** `student-project`, `epic-01` · **Початковий статус:** Backlog.

**Попередній календар:** 15.10.2026 → 23.10.2026 (приймання після review).  
**Оцінка:** 12 год власника + 1 год reviewer; спільні сесії TASK-001/040 враховані окремо в Ганті. [Розрахунок і залежності](../gantt/13_Gantt_Plan.md#gantt-task-002).

**Мета:** Зміни студентів потрапляють у спільну гілку тільки після review та автоматичних перевірок.

**Що і як зробити:** Перенести поточний каркас до погодженого репозиторію без .env, node_modules і локальних даних. Зафіксувати Node 24 для команди, npm ci, npm run check; додати окрему CI-перевірку MongoDB з replica set. Налаштувати main/PR, шаблон PR із сценарієм і результатом перевірок. Описати короткий Git-процес українською.

**Область змін:** .gitignore, package.json, CI-конфігурація обраного Git-hosting, шаблон PR, docs. Наявні файли змінюємо за потребою; нові імена/методи остаточно погоджуємо до Ready, не створюємо порожній каркас наперед.

**Вхід і передумови:** Погоджений hosting і доступи від керівника; поточний код, lockfile та npm-команди.

**Результат здачі:** Відтворюваний checkout і PR із обов’язковими перевірками.

**Покрокове виконання:**

1. Перевірити ignore-правила, не переносити env і локальні дані.
2. Зберегти каркас у спільному репозиторії без втрати змін.
3. Налаштувати npm ci на Node 24 та npm run check.
4. Створити окремий MongoDB-job з rs0, очікуванням PRIMARY і тестовою базою.
5. Налаштувати review та required checks, перевірити права команди.
6. Провести пробний PR із навмисним падінням тесту, потім виправити і записати Git-процес.

**Контрольний приклад:** Чистий checkout іншого учасника зелений; невдалий check не дозволяє прийняти PR.

**Критерії приймання:**

- Чистий checkout встановлюється через npm ci; зміни не втрачають поточний код.
- PR показує перевірки; злиття вимагає reviewer і успішних обов’язкових checks у межах можливостей обраного hosting.
- MongoDB-job перевіряє саме integration, має обмежений час очікування та власну тестову БД; секретів у репозиторії немає.

**Перевірка/демонстрація:** Один навмисно некоректний тест дає червоний check; після виправлення PR зелений. Два студенти проходять checkout → branch → PR.

**Межі:** Не додавати deployment, Kubernetes або нову прикладну інфраструктуру.

## Шаблон підзадачі та дефекту

Підзадача має власний перевірний результат, наприклад «додати умовне резервування місця в repository» або «перевірити дві одночасні спроби зарахування». Вона успадковує правила батьківської Story. Не зводьте всі підзадачі лише до назв файлів: завершення controller без робочого сценарію не означає завершення Story.

Для нової задачі копіюйте поля: Summary; Type; Epic/Parent; мета; передумови; вхід і вихід; що зробити; що не входить; критерії; перевірки; залежності; виконавець; reviewer; розмір; пріоритет. Для важливої умови можна використати Given/When/Then: «Є одне місце; дві різні дитини зараховуються одночасно; одна успішна, інша отримує бізнес-помилку, occupiedSeats не перевищує capacity».

Bug: назва з конкретним симптомом, середовище, безпечні кроки відтворення, очікуваний/фактичний результат, вплив, пов’язана Story, requestId за потреби. Не вставляйте JWT, паролі чи реальні персональні дані у Jira. Дефект суми, доступу чи атомарності блокує приймання відповідного сценарію.
